---
name: Dependency security upgrades
description: Compatibility and legacy-scope decisions for dependency vulnerability remediation.
---

Do not keep unbounded cross-major overrides generated by automated audit fixes without checking the consuming package's module format and API.

**Why:** A broad UUID upgrade can select an ESM-only major for CommonJS consumers. Choose a patched compatible major or upgrade the direct parent to a version that supports the newer module format.

**How to apply:** Inspect parent dependencies and runtime imports, constrain security overrides to verified versions, and build and start both frontend and API services.

Legacy CRM is reference source, not the running MIS application. Check whether a vulnerable declared dependency has an assembly, configuration, or caller before forcing a framework migration.

**Why:** Modern log4net fixes require a newer framework than the legacy .NET 4.0 source. The legacy snapshot's log4net declaration was unused; removing an unused declaration avoids falsely claiming an incompatible upgrade is deployable.

**How to apply:** If logging is introduced into the legacy application later, choose a supported framework and patched logging package together rather than restoring the old dependency.
